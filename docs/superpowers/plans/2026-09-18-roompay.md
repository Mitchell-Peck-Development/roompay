# RoomPay Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build RoomPay — a no-account, per-device roommate bill splitter with opt-in share links and calendar hand-off — as a pnpm/Turborepo monorepo (`apps/app`, `apps/web`, `packages/ui`, `packages/core`) plus the `rp` schema migration.

**Architecture:** All money logic is pure TypeScript in `packages/core`, built test-first. `apps/app` is a client-side shell over a zustand store persisted to `localStorage`; the only server surface is five share routes, a roommate page, and an ICS endpoint, all of which reach Postgres through one `RpBackend` interface (Supabase RPC in production, PGlite running the *same migration SQL* in dev and tests). The database does no maths: the owner's device publishes a computed snapshot.

**Tech Stack:** pnpm 10, Turborepo 2, Next.js 16 (App Router), React 19, Tailwind v4, shadcn/ui (radix base, `nova` preset as the starting point), zod 4, zustand 5, `@supabase/supabase-js`, `@electric-sql/pglite`, vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-09-18-roompay-design.md` — read it first; section numbers below (§) refer to it.

**How this plan is written.** The owner asked for spec → plan → build in one uninterrupted pass, executed inline by the plan's author. So: logic tasks (core, SQL, server) carry their real test cases and exact signatures; UI tasks carry file lists, component contracts and acceptance checks rather than verbatim JSX, because writing every component twice adds no safety. Nothing is left undecided — where a task doesn't show code, the spec section it cites defines the behaviour.

## Global Constraints

- All amounts are integer cents. No floating-point money anywhere. Shares and payments must always sum exactly (§3.1, §3.3).
- No accounts, no names — only arbitrary labels. No payment handles, no free-text note in the share payload (§1, §4.2).
- Never touch the remote Supabase project. Deliver SQL in `supabase/migrations/`; verify it on PGlite only.
- The server never receives the service-role key. Env is `SUPABASE_URL` + `SUPABASE_PUBLISHABLE_KEY` (§4.4).
- Raw link tokens and write keys never reach the database: hash with SHA-256 in the Next.js server (§4.1).
- Secrets travel in POST bodies, never query strings; the token appears only in `/r/[token]…` paths (§4.4).
- Share pages: `noindex`, `Referrer-Policy: no-referrer`, generic metadata with no amounts (§4.5).
- Workspace package scope is `@workspace/*` (what the shadcn monorepo template generates). shadcn components live in `packages/ui`.
- Next.js 16 differs from older versions: before using a Next API (route handlers, `params`, metadata, manifest, `ImageResponse`), read the matching guide in `node_modules/next/dist/docs/`.
- Commit after every task. Never push. Commit messages end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- Commands run from the repo root unless stated. Core tests: `pnpm --filter @workspace/core test`. App tests: `pnpm --filter app test`.
